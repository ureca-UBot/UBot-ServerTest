# 로컬 Redis 장애 검증 — 2026-10-23

**작업 복구 PASS.** 실제 LLM 질문 100건을 처리하던 중 전용 Redis를 SIGKILL로 종료·재기동했다. 재접수 없이 100건 전부 답변이 완료됐고 작업 유실·중복 저장·최종 작업 실패·작업 타임아웃은 0건이다. **장애 중 작업 조회는 2초 제한 안에 응답을 받지 못했다.**

## 환경과 장애 주입

- API `APP_ROLE=api` / 18080 / PID 35608, Worker `APP_ROLE=worker` / 18081 / PID 12436. 장애 전후 PID와 프로세스 시작 지표가 같으며 둘 다 재시작하지 않았다.
- 합성 회원 100명으로 실제 재로그인한 뒤 각자 질문을 한 번 보냈다. 100건 모두 고유 jobId·DB QUEUED로 접수한 뒤 Worker를 시작했다. 질문은 “분실한 유심을 재발급받으려면 어떻게 하나요?”이며 비캐시 FAQ를 사용했다.
- 실제 chat: `RedHatAI/Qwen3-4B-Instruct-2507-quantized.w4a16`, embedding: `BAAI/bge-m3`. RTX 3060 12 GiB, Worker·LLM 동시 실행 각각 4, JVM당 Xms512m/Xmx2g. 모델 모의 처리는 없다.
- 전용 PostgreSQL 25432와 Redis 26379를 사용했다. 개발 DB·Redis는 종료하지 않았다. 대기 제한 10분, 실행 제한 180초, 재발행 기준 30초, 복구 확인 15초, heartbeat 만료 1분을 유지했다.
- Redis는 `appendonly=no`, `save=3600 1 300 100 60 10000`였다. 영속성 설정·볼륨을 변경하지 않고 같은 컨테이너에 `docker kill --signal KILL` 후 `docker start`를 실행했다. exit code 137과 새 run_id를 확인했다. graceful shutdown·FLUSHDB·수동 메시지 재발행은 하지 않았다.
- 08:33:36.220 KST에 모델 실행 중 요청 4건을 관측하고 08:33:36.868에 종료를 요청했다. DB 시작/완료 시각으로 확인한 당시 상태는 실행 4건·대기 96건·완료 0건이었다.

독립 읽기 전용 SQL로 회원 100명·대화 100개·attempt 100개·답변 턴 100개, 결과 참조·소유권·답변 내용·완료 시간을 다시 대조했다. Worker LLM 성공 지표와 모델 서버 성공 카운터 증가량도 각각 100이다.

종료 후 DB snapshot을 받는 사이 4건이 완료돼 첫 snapshot에는 실행 0·성공 4로 보인다. 이 snapshot의 원본 시작/완료 시각을 사용해 장애 시점 상태를 역산했다. 실제 완료는 Redis 종료보다 약 0.44초 뒤였으므로 장애 당시 실행 중이었음을 확인할 수 있다. 원본 snapshot·보고서는 그대로 보존했고 집계 시점 보정에는 단위 테스트 2개를 추가했다.

## 발견한 API 지연

- Redis 중단 중 인증된 작업 GET 6회 모두 클라이언트 2초 제한 안에 응답을 받지 못했다(관측 약 2.00~2.01초). 서버 HTTP 오류 코드가 아니라 클라이언트가 응답을 확보하지 못한 경우다.
- API health 표본 74회 중 6회, Worker health 표본 52회 중 5회가 응답 실패였다. 복구 후에는 동일 API·Worker에서 정상 조회됐고 마지막 100건 GET도 모두 성공했다.
- 따라서 이번 결과는 **작업 복구 성공**이다. Redis 장애 중에도 API가 정상 응답했다고 판정하지 않는다.
- 현재 인증 필터는 매 요청에서 Redis의 토큰 폐기 정보를 읽는다. 이 경로가 조회 지연에 영향을 줄 수 있다는 것은 코드에 근거한 추정이며, 단일 요청의 병목을 확정하는 추적 계측은 이번에 추가하지 않았다. 운영 코드는 변경하지 않았다.
