# 실제 vLLM 워커 4·16·32개 동시 부하 비교

2026-10-22에 시작한 로컬 비교 시리즈. 같은 회원 1,500명·질문·그룹 순서로 새 대화를 만들었다. 실제 Qwen3 4B와 BGE-M3, RTX 3060 12 GiB, 합성 FAQ 3건, 캐시·임계값·가드·DB 연결·힙·대기/실행 제한을 유지했다. 워커 동시 실행 환경변수만 변경했고, 기존 기본값에 따라 LLM 호출 상한도 4·16·32개로 연동됐다. 애플리케이션 소스·.env는 변경하지 않았다.

32개의 전체 완료 시간은 4개 대비 56.53%, 16개 대비 11.03% 감소했다. 음수 감소율은 시간이 늘었다는 뜻이다. 전체 시간은 각 POST 시작부터 DB `finished_at`까지로 인증·접수·워커 대기를 포함하며, 폴링 지연·응답 전달·UI 렌더링을 제외한다. 대기 제외 처리는 `started_at → finished_at`이며 임베딩·검색·가드·모델·저장을 포함한다. SQL `percentile_disc`로 LLM p50/p95를 교차 확인했다.

예상 금지어 `FW-003`와 유사도 미달 `CHAT-013`은 업무상 차단으로 오류·타임아웃에서 제외한다. 타임아웃은 최종 오류 코드 `CHAT-016`(대기/워커), `LLM-004`, `EM-003` 및 HTTP 408/504로 집계한다. 전송 연결 오류가 있다면 세부 타임아웃 여부는 별도 미확인으로 표시한다. 처리 오류와 타임아웃은 중복될 수 있으므로 합산하지 않는다. 모델 호출의 프로세스 지표는 JSON의 프로세스 지표 차이 `modelRequestOutcomes`에서 따로 볼 수 있다. 내부 HTTP 재시도는 별도로 계측하지 않았다.

- 판정: 4개 PASS / 16개 PASS / 32개 PASS. 32개 요청 시작 범위 29ms, k6 종료 0.
- 32개 실행 중 워커 32개·LLM 호출 32개를 관측했고 호출 상한 32개를 확인했다. 실제 답변 표본 3건을 다시 조회해 확인했다.
- 각 동시 실행 수를 한 번씩 측정했고, 뒤의 실행은 전용 DB와 모델 캐시를 재사용했다. 그룹마다 같은 질문을 반복하며 k6·BE·DB·Redis·GPU가 같은 머신을 쓴다. 운영 성능의 보장값이나 최적 동시 실행 수의 통계적 증명으로 일반화할 수 없다.
