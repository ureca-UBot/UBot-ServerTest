# 실제 vLLM 워커 4·16·32·64개 동시 부하 비교

2026-10-23 로컬 64개 추가 측정. 같은 회원 1,500명·질문·그룹 순서로 새 대화를 만들었다. 실제 Qwen3 4B·BGE-M3, RTX 3060 12 GiB, 합성 FAQ 3건, 캐시·임계값·가드·DB 연결·힙·대기/실행 제한을 유지했다. 워커 동시 실행 환경변수만 변경했고, 기존 기본값에 따라 LLM 호출 상한도 4·16·32·64개로 연동됐다. 애플리케이션 소스·.env는 변경하지 않았다.

64개의 전체 완료 시간은 4개 대비 59.25%, 16개 대비 16.58%, 32개 대비 6.24% 감소했다. 음수 감소율은 시간이 늘었다는 뜻이다. 전체 시간은 각 POST 시작부터 DB `finished_at`까지로 인증·접수·워커 대기를 포함하고 폴링 지연·응답 전달·UI 렌더링을 제외한다. 대기 제외 처리는 `started_at → finished_at`이며 실제 임베딩·검색·가드·모델·저장을 포함한다. PostgreSQL `percentile_disc`로 LLM p50/p95를 교차 확인했다.

예상 차단 `FW-003`·`CHAT-013`은 오류에서 제외했다. 타임아웃은 최종 `CHAT-016`(대기/워커), `LLM-004`, `EM-003` 및 HTTP 408/504다. 전송 연결 오류가 있으면 그 세부 타임아웃 여부는 별도 미확인으로 남긴다. 처리 오류와 타임아웃은 중복될 수 있으므로 합산하지 않는다. 프로세스 수준의 LLM 호출 성공/오류는 비교 JSON의 `modelRequestOutcomes`에 별도로 기록했다. 내부 HTTP 재시도는 따로 계측하지 않았다.

- DB의 started_at·finished_at 구간을 겹쳐 계산한 최대 동시 작업은 64개다. 순간 지표에서는 워커 63개·LLM 호출 13개를 관측했고 LLM 호출 상한 64개를 확인했다. 실제 생성 답변 표본 3건을 재조회했다.

- 각 설정을 한 번씩 측정했고, 뒤의 실행은 기존 전용 DB·모델 캐시를 재사용했다. 그룹별 같은 질문을 반복하며 k6·BE·DB·Redis·GPU는 같은 머신을 쓴다. 운영 성능 보장이나 최적 동시 실행 수의 통계적 증명으로 일반화할 수 없다.
